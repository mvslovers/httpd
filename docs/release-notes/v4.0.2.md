HTTPD 4.0.2 is a **relink**: the release artifacts are built against libc370
1.0.4 instead of 1.0.3. No new feature, no breaking change, and no defect of
HTTPD's own — but one behaviour change that is not labelled breaking, and one
correction to the shipped installation guide that matters on the upgrade.

**If you run HTTPD with mvsMF under load, this is the release you want.** The
library fixes below are all in code paths a long-running multitasking started
task uses constantly. Take **ufsd 1.2.2** with it if you serve static files, and
see *[The modules in HTTPD's address space](#the-modules-in-httpds-address-space-need-their-own-relink)* below — they are the part
that is easy to miss.

## Why relink

libc370 ships through the **cc370 sysroot** rather than as a pinned dependency,
so none of it reaches a running system on its own. This relink is the entire
delivery mechanism. Four fixes reach HTTPD:

**Concurrent `printf()` no longer corrupts the stream
([libc370#145](https://github.com/mvslovers/libc370/issues/145)).**
`vvprintf()`'s `%s` and `%eEgGfF` branches called the *public* `fputs()`, and
every `__examin()` conversion went through the public `fputc()`. Those wrappers
lock and **unconditionally unlock** the same FILE, and ENQ/DEQ `RET=HAVE` carries
no nesting count — so the inner unlock released the caller's hold at the first
conversion and everything after it ran unserialized, the `\n`-triggered QSAM PUT
included. Two tasks writing the same FILE merged and truncated records until the
broken PUT surfaced as `ABEND S001-1` with no SYNAD, or as a task silently wedged
in a corrupted QSAM state. It was reported against FTPD, where parallel transfers
made it likely; HTTPD's worker pool is the same shape of exposure.

**`puts()` is one critical section now, and `fclose()` no longer tears the FILE
down outside the lock (#147).** The same class of defect, one step further in:
`fclose()` flushed, closed the DCB and freed both buffer and FILE with no hold on
the lock, so a concurrent write could land on a closed DCB or through freed
storage.

**`DEQ` no longer drops the scope bits (#147).** `__enqdeq()`'s DEQ branch
overwrote `pl.opt` instead of OR-ing into it, so every DEQ went out `SCOPE=STEP`
and could never release a `SCOPE=SYSTEM` ENQ.

**Four external names were each exported by two archived objects (#151).** The
archive namespace is flat and eight characters wide, and ld370 satisfies an
autocall from the first object offering a name. Three were harmless twins;
`@@ERRNO` was not — one object held the per-task accessor behind that name, the
other a `DC F'0'`. Every `errno` in the ecosystem compiles to a call through
`V(@@ERRNO)`, so the wrong resolution would branch onto four zero bytes, an
invalid opcode, on the first `errno` touch. Never observed: link order happened
to pick the right object, and nothing enforced it. It is enforced now.

`fprintf()` was never affected — it formats into a private buffer and issues one
`fwrite()`.

## Not labelled breaking, but read it

libc370 1.0.4 plants a **SYNAD** on the DCBs its stdio layer opens, so an
uncorrectable I/O error — bad track, wrong-length record, device error — becomes
`ferror()` + `errno EIO` instead of ABEND S001. For a server that is plainly the
right trade.

The other side of it is that **`feof()` is deliberately not set**, so a loud
failure becomes a silent one wherever a read loop treats the resulting `NULL` as
end of data. HTTPD had exactly one such place, and it is the configuration:

```c
while (fgets(line, sizeof(line), fp)) parse_line(httpd, line);
```

A read error on `DD:HTTPPRM` ended that loop exactly as the end of the member
does. Everything past the failed block was then silently absent — the port, the
document root, and **every `MOD=`/`LOC=` route with the `AUTH=` policy attached
to it** — and the start went on regardless. That is the same hazard `HTTPD420E`
refuses to start on, arriving through the reader instead of the parser.

It now abandons the start, `CC 0008`:

```
HTTPD038E READ ERROR ON DD:HTTPPRM -- CONFIGURATION INCOMPLETE
```

**Measured on MVS**, with the error vector libc370's own probe established: the
same data set behind two DDs that disagree about `BLKSIZE`, so the first READ
meets a 3120-byte block with an 80-byte buffer. `TSTPRM` runs it on the batch and
the TSO leg, and the first round reads the member healthy so the second cannot
pass on a read that failed for some other reason:

```
guard removed (JOB03088)   round 2: rc=0 errno=5 port=8080 maxtask=9
shipped       (JOB03090)   round 2: rc=8 errno=5, start abandoned
```

The first line is the defect in one row. `PORT=2280` and `MAXTASK=17` are in the
member that was just read successfully; the failing round came back with 8080 and
9 — the built-in defaults, nothing parsed at all — and reported success. **A
server on that configuration has no routes whatsoever** and says nothing but its
normal banner. The shipped build refuses it.

### What did not need a guard

The CLIB `fread()`/`fgets()` branches in `httpfile.c` are dead code since 4.0.0:
`http_open()` returns NULL unconditionally, so `httpc->fp` is never non-NULL and
static files are served exclusively through libufs. They are left as they are
rather than guarded for a condition that cannot arise.

### Deliberately not fixed here

HTTPD's debug and trace output goes to `DD:HTTPDBG` through the same stdio layer.
With the SYNAD in place, an I/O error there now leaves the started task **running
with tracing silently dead** rather than abending. That is only reachable with
`DEBUG=1`, and fixing it properly needs the fail-fast / `clearerr()` decision
still open as
[libc370#149](https://github.com/mvslovers/libc370/issues/149) — the same
reasoning FTPD applied to its own log. Recorded rather than patched around.

## The modules in HTTPD's address space need their own relink

This is the part that is easy to miss, and it is specific to HTTPD.

**mvsMF, HTTPLUA and HTTPREXX are separate load modules with their own
statically linked C runtime.** They run in HTTPD's address space, dispatched into
HTTPD's task by the LINK SVC, but relinking the server does nothing for them.
The library fixes above reach a module only when **that module** is rebuilt
against libc370 1.0.4.

So `HTTPD005I` tells you what the *server* linked against and nothing more. If
you route `/zosmf/*` to mvsMF, the runtime actually executing those requests is
mvsMF's own copy.

## What is running

`HTTPD005I` stamps the library the module was actually linked against, so a
deploy that did not take cannot hide:

```
HTTPD000I HTTPD 4.0.2 (<commit>) STARTING
HTTPD005I LIBC370 1.0.4 (1CA9E04)
```

If that second line still reads `1.0.3`, the started task is running the old
module — that line is the point of the release.

## The installation guide corrects a dataset name

`<vrm>`, the MVS dataset qualifier, **carries the patch level**: `V4R0M0` for
4.0.0, `V4R0M1` for 4.0.1, `V4R0M2` for 4.0.2. The FMID does not — `THTP400`
names the whole 4.0.x functional level.

The shipped guide did not say so. It gave `V4R0M0` as the example without saying
what varies, and spelled `HTTPD.V4R0M0.WEBROOT.UFS` literally in six operator
commands. Since the guide travels in the archive **as** `README.md`, the 4.0.1
package went out naming datasets its own install job never created. Corrected
here, and section 12 now says which of its steps a patch upgrade runs — see
below, because that is where the wrong reading costs something.

## Installing

Download **`httpd-4.0.2-dist.zip`** (or `.tar.gz`). It holds everything needed
and a step-by-step guide:

| | |
|---|---|
| `README.md` | the installation guide |
| `httpd-4.0.2-load.xmit` | the five load modules |
| `httpd-4.0.2-samplib.xmit` | the STC procedure, the configuration pattern, and a job for the webroot |
| `httpd-4.0.2-alloc.jcl` | allocate the datasets — run once |
| `httpd-4.0.2-inst.jcl` | receive, apply, accept |
| `httpd-webroot.img` | the document root as a UFS370 disk image |

Upload the two XMITs in **binary**, submit the allocation job once, then the
install job — the only lines to edit are the two dataset names you uploaded to.
The SYSMOD travels inline in the job, so there is no third file to transfer.

Everything lands under `HTTPD.V4R0M2.*`, so it does not collide with an existing
`V4R0M0` or `V4R0M1` installation. Copying the procedure and the configuration
pattern into your PROCLIB and PARMLIB stays a manual step, by design: the product
owns the patterns, your system owns the copies. The guide says which member goes
where.

FMID is **`THTP400`**.

The webroot image rides neither SMP nor TSO RECEIVE — SMP has no element type for
a `DSORG=PS/RECFM=U` image and must never touch site content, and RECEIVE refuses
to merge into an existing dataset. It travels as a plain file and goes up over
`IND$FILE`, which needs nothing on the target beyond a 3270 session. Step 9 of
the guide is that transfer, and it is the one place you substitute `<vrm>`
yourself.

## Upgrading from 4.0.1

An FMID names a *functional level*, one per minor release, so 4.0.2 ships as
`THTP400` again — the id 4.0.1 already applied **and accepted**, and SMP will not
apply a function SYSMOD that is already applied.

| | |
|---|---|
| **Keeping it SMP-managed** | Free the FMID first with the `UCLIN` job in section 12 of the shipped guide, then run the 4.0.2 allocation and install jobs as for a fresh install |
| **Without SMP** | Receive `httpd-4.0.2-load.xmit` into a library and point the procedure's `STEPLIB` at it |

**Run only the `UCLIN` step of section 12, not its `DELETE` step.** The libraries
are versioned per *patch* — `HTTPD.V4R0M2.*` here — so the new install never
touches 4.0.1's, and the `DELETE` names the old release's datasets. Scratching
them is a choice about the predecessor, not a step of this upgrade; after the
`UCLIN` they are orphans with no inventory record, and leaving them is fine.
Read `<vrm>` as the release you are removing and check the name against ISPF 3.4
before running anything there.

Check the inventory before and after with the zone operand — it is mandatory,
`LIST SYSMODS .` is SMP/E syntax and gets `HMA2033`:

```
LIST CDS  SYSMOD(THTP400) .
LIST ACDS SYSMOD(THTP400) .
```

`RC 04` with an empty list means the id is free.

The configuration member and the procedure are unchanged from 4.0.1, and so is
the webroot image — if yours is already mounted and you did not change it, step 9
has nothing for you.
