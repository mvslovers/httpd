HTTPD (httpd) 4.2.0 is the HTTP server for MVS 3.8j rebuilt on the current
C toolchain — CC/370 (cc370) 1.6.1 and LIBC/370 (libc370) 2.10.3 — with one
change in behaviour: every explicit login now gets a session of its own. From
4.1.0 it is a **drop-in upgrade**: stop the server, run the install job, start
it. Nothing is allocated, nothing is uninstalled first, and the dataset names
do not move.

## Read this first

- **Coming from 4.0.x? Install 4.1.0 first.** This release's SYSMOD deletes
  `THTP410` and nothing else. On a 4.0.x system the load modules still belong
  to `THTP400`, and SMP will not let a SYSMOD replace a module it does not own:
  the install selects nothing, copies nothing, and every step still ends
  `RC 00`. 4.1.0 is the release that crosses from `THTP400` and moves to the
  unversioned dataset names; section 12a of its guide has the order. Then
  upgrade to 4.2.0 the ordinary way.
- **Two clients that log on with the same userid and password from the same
  address no longer share a token** — through the `/login` form, and through a
  module's login endpoint once that module calls the new `http_new_session()`.
  A module built for 4.1.0 still hands out the shared token until it is
  updated. See *Sessions* below.
- **For authors of server modules:** a module built against 4.1.0 runs
  unchanged — the function vector is append-only. A module that calls the new
  `http_new_session()` (vector offset `0x144`) needs HTTPD 4.2.0; there is no
  run-time test for a vector entry, so on an older server the call goes
  through whatever lies at that offset. The library archive
  `httpd-4.2.0-lib.tar.gz` is built for LIBC/370 2.x, so a module built
  against it needs that runtime generation as well.
- **Modules running in HTTPD's address space need their own update.** They are
  separate load modules, each linked against its own copy of LIBC/370.
  Updating HTTPD does not relink them.

## Sessions

Up to 4.1.0 HTTPD cached one credential per *address, userid and password*. A
second client logging on with the same credentials from the same address — two
browser tabs, or two tools behind one NAT — got the same cached credential and
the same token. When one of them logged out, the credential was deleted and the
other client's next request answered `401`.

Now each explicit login — the `/login` form, and a module's login endpoint
that calls `http_new_session()` — gets a credential of its own: its own token
and its own RACF ACEE, so a logout ends only that session. The session limits
(`SESSION_TIMEOUT`, `SESSION_MAXAGE`) apply to each session separately.

One client (same userid, password and address) holds at most **16** sessions.
The next login ends its least recently used one, provided that one has been
idle for at least 60 seconds; if none has, the login is refused rather than
ending a session that a request may be using. A client that never logs out
therefore cannot fill the credential store for everyone else.

Plain Basic requests are unchanged: they resolve through the shared cache, as
before.

A login now costs **one more RACF logon**: the session gets its own ACEE, and
the shared credential the login resolved through stays cached beside it. A
security log therefore shows up to two logons per explicit login, and each
login takes up to two slots in the credential store.

## Before and now

| | 4.1.0 | 4.2.0 |
|---|---|---|
| Two logins, same userid/password/address | share one token; a logout ends both | one session each; a logout ends one |
| Logins per client | unbounded, one shared credential | at most 16 sessions, least recently used one ends first |
| A module built from the library archive, started with a 1–3 byte parameter whose third byte is zero | started with an empty `argv[0]` | starts with its own name — the five shipped modules have it; another module needs a relink against `httpd-4.2.0-lib.tar.gz` |
| `F HTTPD,D M` when its recovery environment cannot be set up | reported as `ABEND SFFF` | reports the failure itself |
| A server-side include whose buffer count went negative | skipped a flush it needed | flushes |
| Server startup | its own copy of the C runtime start-up, which had fallen behind | the runtime's start-up, with HTTPD's two steps (refuse `SYSPRINT`/`SYSTERM`/`SYSIN`, open `HTTPDOUT`/`HTTPDERR`/`HTTPDIN`) as a hook — same messages, same order |
| C runtime | LIBC/370 1.0.6 | LIBC/370 2.10.3 |

## The C runtime — LIBC/370 2.10.3

This is a new major generation of the runtime under every module: the headers
were reorganised, and SHA-256, Blowfish and base64 moved out into a library of
their own. When HTTPD was ported to the 2.0 generation, the generated
assembler of every source was compared against the 1.0.x build: apart from
compiler label numbering, only the calls to base64 differ.

Two runtime changes are worth knowing about:

- **A failed write to a partitioned data set member no longer destroys the
  member.** When a write ran out of space, the close still put the member into
  the directory: a new member appeared with no records, and an existing one was
  replaced by whatever had reached the disk. Now the close leaves the directory
  alone after a failed write. HTTPD itself writes no PDS member unless
  `DD:HTTPDBG` points at one. A module in its address space carries its own
  copy of the runtime and gets this fix only when it is relinked.
- **stdio no longer takes a lock on a stream before the first thread exists.**
  HTTPD creates its socket thread and worker pool through the runtime's thread
  services, so its streams are locked exactly as before once it is serving.

## What is running

`HTTPD005I` names the runtime the module was linked against, so a deploy that
did not take cannot hide:

```
HTTPD000I HTTPD 4.2.0 (xxxxxxx) STARTING
HTTPD005I LIBC370 2.10.3 (A790DC4)
```

If either line still reads 4.1.0 or LIBC370 1.0.6, `STEPLIB` names a library
that does not hold this release, and you are running the old build.

## Installing

Download **`httpd-4.2.0-dist.zip`** (or `.tar.gz`). It holds everything needed
and a step-by-step guide:

| | |
|---|---|
| `README.md` | the installation guide |
| `httpd-4.2.0-load.xmit` | the five load modules |
| `httpd-4.2.0-samplib.xmit` | the STC procedure, the configuration pattern, and a job for the webroot |
| `httpd-4.2.0-alloc.jcl` | allocate the datasets — first install only |
| `httpd-4.2.0-inst.jcl` | receive, apply, accept |
| `httpd-webroot.img` | the document root as a UFS370 disk image |

The FMID is **`THTP420`**, and it deletes `THTP410`.

**Upgrading from 4.1.0:**

1. `/P HTTPD` — the APPLY rewrites the library the running server loads from.
2. Upload the two XMITs in binary and submit the install job. **Skip the
   allocation job**: `HTTPD.LINKLIB` and `HTTPD.AHTTPLOD` already exist and hold
   4.1.0, which is what the APPLY expects to replace. The webroot disk is
   yours; leave it as it is.
3. Expect the APPLY to end `COND CODE 0004` on `HMA2461 … NOT FOUND ON
   SMPSCDS LIBRARY`: the deleted level has no backup entry. The ACCEPT still
   runs.
4. **Verify by listing `HTTPD.LINKLIB`**, not by the condition codes: five
   members, with one `HMA2380 COPY SUCCESSFUL` line per module in the SMP
   output. A condition code says whether a step ran, not what is on the disk.
5. `/S HTTPD` and read the banner above.

`THTP410` stays in both SMP zones as a tombstone (`TYPE = FUNCTION`,
`DELBY = THTP420`), which `LIST` reports at RC 00. That is correct: the id is
spent. Section 12 of the guide removes HTTPD and names every id it has ever
spent, so no tombstone is left behind.

**A first install** is the guide from the top: allocation job, install job,
procedure and configuration, the webroot disk.

Without SMP: receive `httpd-4.2.0-load.xmit` into a library and point `STEPLIB`
at it.

## What is not in this release

The open defects carried over from 4.1.0 are unchanged, among them
[#263](https://github.com/mvslovers/httpd/issues/263) (a UFS read error is
served as a truncated body) and
[#264](https://github.com/mvslovers/httpd/issues/264) (with `DEBUG=1`, an I/O
error on `DD:HTTPDBG` leaves tracing silently dead).

## Changes since 4.1.0

- Each explicit login gets a session of its own; new vector entry
  `http_new_session()` at `0x144` ([#288](https://github.com/mvslovers/httpd/issues/288))
- Built with CC/370 1.6.1 and LIBC/370 2.10.3 ([#292](https://github.com/mvslovers/httpd/issues/292));
  ported to LIBC/370 2.0, with crypto370 for SHA-256, Blowfish and base64
  ([#272](https://github.com/mvslovers/httpd/issues/272))
- The server start-up is the runtime's, with HTTPD's two steps as a hook
  ([#281](https://github.com/mvslovers/httpd/issues/281))
- A 1–3 byte parameter with a zero third byte is no longer taken for a TSO
  command buffer ([#275](https://github.com/mvslovers/httpd/issues/275))
- Two defects found by `-Wextra`: the `D M` recovery failure and the SSI flush
- Built against UFSD 1.4.0
