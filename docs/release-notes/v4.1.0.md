HTTPD 4.1.0 changes **no source code at all**. Not one file under `src/`,
`include/` or `asm/` differs from 4.0.2. What it changes is how the product is
named on your system and how one release replaces another — and it relinks
against libc370 1.0.6 on the way through.

**Read *[Upgrading from 4.0.x](#upgrading-from-40x)* before you download
anything.** The dataset names change in this release and never again, which
makes this one upgrade a move rather than a replacement. It is not difficult,
but it is not the usual three steps either.

## The dataset names carry no version

`HTTPD.LINKLIB` — that is the whole change, and it is the one users asked for
([#259](https://github.com/mvslovers/httpd/issues/259)).

| | 4.0.x | 4.1.0 |
|---|---|---|
| Target library | `HTTPD.V4R0M2.LINKLIB` | `HTTPD.LINKLIB` |
| Sample library | `HTTPD.V4R0M2.SAMPLIB` | `HTTPD.SAMPLIB` |
| Distribution library | `HTTPD.V4R0M2.AHTTPLOD` | `HTTPD.AHTTPLOD` |
| Webroot | `HTTPD.V4R0M2.WEBROOT.UFS` | `HTTPD.WEBROOT.UFS` |

Up to 4.0.2 the qualifier carried the **patch** level while the FMID moved only
per minor, so two releases never collided on their libraries — only on the FMID.
That asymmetry is what made a patch install need `UCLIN` to free the id, and it
is what made the uninstall job's `DELETE` step a trap: it named the
*predecessor's* datasets, so running it scratched libraries nobody was using
while the live installation stood untouched, with SMP reporting success
throughout. One set of names ends that. There is one installation, and the
inventory and the disk can no longer drift apart.

There is no `<vrm>` placeholder in the shipped guide any more. Nothing is left
for you to substitute.

## An upgrade no longer uninstalls anything first

Each release's SYSMOD now carries `++VER(Z038) DELETE(<previous FMID>)`
([#269](https://github.com/mvslovers/httpd/issues/269)). SMP deletes the old
load modules from the target library and copies the new ones in during the same
`APPLY`, and ownership of each module transfers with them. **The `UCLIN` step
that used to open every upgrade is gone.**

That matters more than it sounds, because without it an upgrade does not fail —
it *succeeds emptily*. SMP keys element ownership on `MOD(name)` in the CDS and
not on the library the element lives in, so a SYSMOD that does not own
`MOD(HTTPD)` may not install it: the element summary prints `MOD HTTPD NOT SEL`,
nothing is copied, and RECEIVE, APPLY and ACCEPT all end `RC 00` with
`HMA2270 … SUCCESSFULLY COMPLETED` — into an empty target library
([#266](https://github.com/mvslovers/httpd/issues/266)).

Measured end to end on a TK5 stand, 2026-09-14, with throwaway ids and the real
module names:

```
HMA2240 SUCCESSFULLY DELETED LMOD HTTPD ON LINKLIB LIBRARY      (x5)
HMA2380 COPY SUCCESSFUL - MOD=HTTPD - LMOD=HTTPD - SYSMOD=...   (x5)
MOD(HTTPD)  FMID = <new>   RMID = <new>
```

Two things that run showed which no amount of reading would have:

**The predecessor's library is left completely intact**, every member still in
place. SMP resolves the ddname `LINKLIB` *in its own job*, and both generations'
libraries end in that qualifier — so the delete lands on the new library and the
old dataset is never opened. Your old installation stays runnable until you
scratch it yourself, which is why the guide has you scratch it last.

**The `APPLY` step ends `COND CODE 0004`, and that is correct.** A deleted level
has no `SMPSCDS` backup entry and never will, so `HMA2461 … NOT FOUND ON SMPSCDS
LIBRARY` follows the success message. The `ACCEPT` step is gated `(4,LT,…)` for
exactly this and still runs. A first install ends `RC 00` throughout.

## FMID

**`THTP410`**, and it deletes `THTP400`. One id per release from now on — 4.1.1
will be `THTP411` deleting `THTP410`.

A SYSMOD id is seven characters, so **no version component may ever exceed 9**.
At patch 9 the next release is a new minor. `4.1.10` cannot be expressed and
will not be released.

`THTP400` is spent. After you upgrade it remains in the inventory as a tombstone
(`TYPE = FUNCTION`, `DELBY = THTP410`) which `LIST` reports at **RC 00**, not
RC 04. That is correct — the id is spent and can never be reused. Section 12 of
the guide says how to clear tombstones if you want a tidy inventory, and why you
must read the inventory rather than write the list from memory.

## The relink — libc370 1.0.6

The artifacts are built against **libc370 1.0.6** instead of 1.0.4. libc370
ships through the cc370 sysroot rather than as a pinned dependency, so a relink
is the entire delivery mechanism. Two changes reach HTTPD:

**An out-of-space write is a return code, not an ABEND
([libc370#176](https://github.com/mvslovers/libc370/issues/176)).** A write that
fills the last track no longer takes `SD37`: `fwrite()`/`fflush()` return,
`ferror()` is set, and `errno` is `ENOSPC`. What it removes is worse than the
abend it replaced — re-driving a WRITE against a DCB that had taken an x37 gave
`0C4` on one run and `0C6` on another for identical code.

**A stream that has failed now fails fast (#149).** Before, a write after an
error was accepted into the FILE buffer and dropped at flush time: measured
upstream, 46 of 50 writes after `ENOSPC` returned full length and not one of
those records reached the disk. `clearerr()` lifts the refusal.

**Neither reaches an HTTP response.** `http_send()` goes to `send()` on the
socket and never through a `FILE*`, so nothing a client sees can be affected.
HTTPD's own logging is `wtof()`, not stdio. The exposure is limited to
diagnostic output — `DD:HTTPDBG` under `DEBUG=1`, and a CGI module's
`stdout`/`stderr`. That audit is
[#265](https://github.com/mvslovers/httpd/issues/265); the remaining work on
those writers is [#264](https://github.com/mvslovers/httpd/issues/264) and is
deliberately not in this release.

## The modules in HTTPD's address space need their own relink

HTTPD does not carry them, and this release does not update them. **mvsMF**,
**httplua** and **httprexx** are separate load modules that run in HTTPD's
address space, each linked against its own copy of libc370. Relinking HTTPD does
nothing for them. If you run mvsMF, take its matching release too.

## What is running

`HTTPD005I` stamps the library the module was actually linked against, so a
deploy that did not take cannot hide:

```
HTTPD000I HTTPD 4.1.0 (D329BB8) STARTING
HTTPD005I LIBC370 1.0.6 (48AAA29)
```

On an upgrade this is the check that matters, and it is a **gate, not a
formality**: if either line still reads the release you came from, `STEPLIB`
still names the old library and you are running the old build. Nothing else
reports that.

## Installing

Download **`httpd-4.1.0-dist.zip`** (or `.tar.gz`). It holds everything needed
and a step-by-step guide:

| | |
|---|---|
| `README.md` | the installation guide |
| `httpd-4.1.0-load.xmit` | the five load modules |
| `httpd-4.1.0-samplib.xmit` | the STC procedure, the configuration pattern, and a job for the webroot |
| `httpd-4.1.0-alloc.jcl` | allocate the datasets — run once |
| `httpd-4.1.0-inst.jcl` | receive, apply, accept |
| `httpd-webroot.img` | the document root as a UFS370 disk image |

Upload the two XMITs in **binary**, submit the allocation job once, then the
install job — the only lines to edit are the two dataset names you uploaded to.
The SYSMOD travels inline in the job, so there is no third file to transfer.

Copying the procedure and the configuration pattern into your PROCLIB and
PARMLIB stays a manual step, by design: the product owns the patterns, your
system owns the copies. The guide says which member goes where.

**Verify the install by listing `HTTPD.LINKLIB`**, not by the condition codes.
Five members, `HTTPD` with `AUTH REQ = YES`. The guide ends with an `IEHLIST
LISTPDS` job for it, because a condition code reports whether a step ran, not
what is on the disk afterwards.

The webroot image rides neither SMP nor TSO RECEIVE — SMP has no element type
for a `DSORG=PS/RECFM=U` image and must never touch site content, and RECEIVE
refuses to merge into an existing dataset. It travels as a plain file and goes
up over `IND$FILE`. **On an upgrade, skip that step**: `HTTPD.WEBROOT.UFS` is
very likely the disk you are already serving, and it is the one dataset no part
of this release scratches.

## Upgrading from 4.0.x

`HTTPD.LINKLIB` does not exist on a 4.0.x system, so nothing of this release
lands on top of anything. **This upgrade is a move, and it is the last one that
is.** Section 12a of the shipped guide has the full order; in short:

| | |
|---|---|
| 1 | `/P HTTPD` — not optional, the APPLY rewrites the library the running server loads from |
| 2 | Run the allocation job. This is the one upgrade that allocates: the names are new on your system |
| 3 | Upload and install as for a fresh install. **No `UCLIN`, nothing to remove first** |
| 4 | Re-point `STEPLIB` in your `HTTPD` procedure to `HTTPD.LINKLIB` |
| 5 | **Replace** the `IEAAPF00` entry if you use APF rather than RAKF — remove the old line, do not just add the new one |
| 6 | Copy over any module that was not ours. `MVSMF` lives in the same library and SMP knows nothing about it |
| 7 | `/S HTTPD` and read the banner. Do not continue until it says 4.1.0 |
| 8 | Only now scratch `HTTPD.V4R0M*.*` |

Two of those deserve their reasons spelled out.

**Step 5 is not tidiness.** An APF entry is a dataset name *plus* a volume
serial, and the list is read only at IPL — so an old entry left beside the new
one survives to the next one, and it stays dangerous after you scratch the
library in step 8: allocate anything with that name on that volume later and it
is APF-authorised with nobody asking. For an `AC(1)` product that is not a
loose end worth leaving.

**Steps 4 to 8 are a deliberate rollback window, then a scratch.** Both
installations sit on the disk side by side until you close it, so a bad start at
step 7 is one procedure edit away from being undone. Close the window; do not
leave the system in it.

Without SMP: receive `httpd-4.1.0-load.xmit` into a library and point `STEPLIB`
at it. The FMID mechanics above do not apply to you.

## Upgrading from 4.1.0 to a later release

Worth saying now, because it is the point of the change: from 4.1.1 on an
upgrade is stop, install, start. The names do not move again, so the allocation
job is **skipped** — the libraries are already there holding the predecessor,
which is exactly what the `APPLY` expects to find and replace.

## What is not in this release

No source change, so nothing in the server behaves differently except what the
relink brings. The open defects carried over from 4.0.2 are unchanged, including
[#263](https://github.com/mvslovers/httpd/issues/263) — a UFS read error is
served as a truncated body — which has behaved that way since 4.0.0 and is not a
regression here.
