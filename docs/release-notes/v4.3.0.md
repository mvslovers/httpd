HTTPD (httpd) 4.3.0 is the HTTP server for MVS 3.8j, rebuilt on LIBC/370
(libc370) 2.12.1 to stop a storage leak. Every request that runs a server
module lost about 128 bytes of the address space's free storage for good.
After a few tens of thousands of such requests no module could be loaded any
more until the server was restarted. HTTPD's own source is unchanged since
4.2.0, and the toolchain is CC/370 (cc370) 1.6.1. From 4.2.0 it is a
**drop-in upgrade**: stop the server, run the install job, start it.

## Read this first

- **This release fixes only the modules it ships.** The leak is in the C
  runtime that every server module carries in its own load module, so it is
  fixed per module, by relinking that module against LIBC/370 2.12.1:
  - The three display modules and `ABEND0C1` in this release are relinked.
  - Any other module running in HTTPD's address space keeps losing storage
    until it is rebuilt against 2.12.1 itself. That includes a REST API
    module, a scripting module, or your own.
  - Updating HTTPD does not relink them.
- **Coming from 4.1.0 or 4.0.x? Go through each release in turn.** This
  release's SYSMOD deletes `THTP420` and nothing else. On an older system the
  load modules still belong to an older id, and SMP will not let a SYSMOD
  replace a module it does not own: the install selects nothing, copies
  nothing, and every step still ends `RC 00`. From 4.1.0, install 4.2.0 first.
  From 4.0.x, install 4.1.0 (section 12a of its guide), then 4.2.0.
- **For authors of server modules:** nothing changes at the interface. The
  function vector is the same as in 4.2.0, and a module built for 4.2.0 runs
  unchanged — but rebuild it against LIBC/370 2.12.1 to get rid of the leak.

## The leak

HTTPD runs a server module with LINK, once per request. Every C program,
a module included, sets up its runtime when it starts and takes it down when
it ends.

- **What leaked:** one piece of that setup, a small table recording the
  program's task, was emptied at the end but never freed. The storage that
  held the only pointer to it was then released, so the table could never be
  freed afterwards: 128 bytes per run.
- **How it grew:** about one 4 K page of free storage lost per 32 module
  requests.

Measured on MVS:

- **The runtime alone:** a program that LINKed an empty C module 2,000 times
  lost 128 bytes per LINK with LIBC/370 2.12.0, and nothing with 2.12.1.
- **The running server:** 900 requests to a module relinked against 2.12.1
  left the free storage exactly where it was. In the same window, an unfixed
  module lost up to 137 bytes per request, and 300 requests that HTTPD answered
  itself, without a module, lost nothing.

The startup stack of a module is a single 262,144-byte request. Once the
leak has eaten into the free storage far enough, that request fails and every
module request fails with it. With about 7 MB free after a start, that is
roughly 50,000 module requests.

## Before and now

| | 4.2.0 | 4.3.0 |
|---|---|---|
| Free storage per request that runs one of the shipped modules | 128 bytes lost for good | unchanged |
| Free storage per request answered by HTTPD itself | unchanged | unchanged |
| Server modules from elsewhere | leak until rebuilt against 2.12.1 | leak until rebuilt against 2.12.1 |
| C runtime | LIBC/370 2.10.3 | LIBC/370 2.12.1 |

## The C runtime — LIBC/370 2.12.1

Besides the leak, the runtime between 2.10.3 and 2.12.1 brings two
additions and one fix, none of which HTTPD itself uses:

- `tryinfo()` reports where an abend caught by `try()` happened.
- `__fx37()` reports which x37 abend a write that ran out of space stood for.
- A data set that fills its 16th extent now reports `ENOSPC`,
  where it reported `EIO`.

## What is running

`HTTPD005I` names the runtime the module was linked against, so a deploy that
did not take cannot hide:

```
HTTPD000I HTTPD 4.3.0 (xxxxxxx) STARTING
HTTPD005I LIBC370 2.12.1 (0C5E84F)
```

If either line still reads 4.2.0 or LIBC370 2.10.3, `STEPLIB` names a library
that does not hold this release, and you are running the old build.

## Installing

Download **`httpd-4.3.0-dist.zip`** (or `.tar.gz`). It holds everything needed
and a step-by-step guide:

| | |
|---|---|
| `README.md` | the installation guide |
| `httpd-4.3.0-load.xmit` | the five load modules |
| `httpd-4.3.0-samplib.xmit` | the STC procedure, the configuration pattern, and a job for the webroot |
| `httpd-4.3.0-alloc.jcl` | allocate the datasets — first install only |
| `httpd-4.3.0-inst.jcl` | receive, apply, accept |
| `httpd-webroot.img` | the document root as a UFS370 disk image |

The FMID is **`THTP430`**, and it deletes `THTP420`.

**Upgrading from 4.2.0:**

1. `/P HTTPD` — the APPLY rewrites the library the running server loads from.
2. Upload the two XMITs in binary and submit the install job. **Skip the
   allocation job**: `HTTPD.LINKLIB` and `HTTPD.AHTTPLOD` already exist and hold
   4.2.0, which is what the APPLY expects to replace. The webroot disk is
   yours; leave it as it is.
3. Expect the APPLY to end `COND CODE 0004` on `HMA2461 … NOT FOUND ON
   SMPSCDS LIBRARY`: the deleted level has no backup entry. The ACCEPT still
   runs.
4. **Verify by listing `HTTPD.LINKLIB`**, not by the condition codes: five
   members, with one `HMA2380 COPY SUCCESSFUL` line per module in the SMP
   output. A condition code says whether a step ran, not what is on the disk.
5. `/S HTTPD` and read the banner above.

`THTP420` stays in both SMP zones as a tombstone (`TYPE = FUNCTION`,
`DELBY = THTP430`), which `LIST` reports at RC 00. That is correct: the id is
spent. Section 12 of the guide removes HTTPD and names every id it has ever
spent, so no tombstone is left behind.

**A first install** is the guide from the top: allocation job, install job,
procedure and configuration, the webroot disk.

Without SMP: receive `httpd-4.3.0-load.xmit` into a library and point `STEPLIB`
at it.

## What is not in this release

The open defects carried over from 4.2.0 are unchanged, among them
[#263](https://github.com/mvslovers/httpd/issues/263) (a UFS read error is
served as a truncated body) and
[#264](https://github.com/mvslovers/httpd/issues/264) (with `DEBUG=1`, an I/O
error on `DD:HTTPDBG` leaves tracing silently dead).

## Changes since 4.2.0

- Built against LIBC/370 2.12.1, which no longer leaks 128 bytes per run of a
  LINKed module ([#297](https://github.com/mvslovers/httpd/issues/297))
